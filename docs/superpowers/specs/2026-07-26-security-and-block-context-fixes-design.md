# PostCrafts: Security Hardening & Block Context Fix — Design

Date: 2026-07-26
Status: Approved for planning

## Background

A full-plugin audit (covering block metadata, block context, React patterns, REST/AJAX design, security, performance, i18n, accessibility, architecture, and tooling) surfaced ten categories of findings. This spec scopes the two categories judged correctness-critical for immediate action:

1. **Security vulnerabilities** in the REST API and AJAX pagination handler.
2. **Block context gap** — the block does not use Gutenberg's `usesContext` mechanism to resolve the current post ID, and a related bug causes the editor preview to diverge from front-end rendering.

The plugin is **live with existing content** on real sites, so all fixes must be backward compatible: no attribute schema changes, no changes to stored post meta format, and no migration routine. Remaining audit findings (asset dependency management, accessibility gaps in AJAX pagination, unused test tooling, minor i18n/schema nits) are out of scope for this spec — see "Out of scope" below.

## Fix 1: Stored XSS in dynamic style output

**File:** `inc/classes/class-style-loader.php`

**Problem:** `print_css()` (line 62-69) echoes `$this->css` — sourced from the `post-crafts-style` / `post-crafts-preview-style` post meta — directly into `<style>` tags in `wp_head` with no sanitization. Any actor able to write to that meta key (see Fix 2) can inject arbitrary markup, including `</style><script>`, that executes for every visitor of the affected post.

**Fix:**
- In `print_css()`, sanitize `$this->css` with `wp_strip_all_tags()` immediately before output. CSS content has no legitimate use for HTML tags or angle brackets, so stripping tags entirely is safe and fully closes the injection vector.
- As defense in depth, apply the same `wp_strip_all_tags()` sanitization to the `style` parameter in `Api::save_style()` (`inc/classes/class-api.php`) before it is persisted, so the stored meta itself never contains injected markup.

**No migration needed:** per decision, existing stored style meta is not retroactively scanned/cleaned — it was generated by the plugin's own CSS generator, and there is no evidence of prior exploitation (the IDOR in Fix 2 is what would have enabled abuse). Only the fix-forward is in scope.

## Fix 2: Broken object-level authorization (IDOR) on style save endpoint

**File:** `inc/classes/class-api.php`

**Problem:** The `POST /post-crafts/v1/style` route (lines 43-65) uses a permission callback that only checks the blanket `edit_posts` capability:

```php
'permission_callback' => function () {
    return current_user_can( 'edit_posts' );
},
```

This does not verify the caller may edit the *specific* `post_id` in the request body. Any user holding `edit_posts` (e.g. a Contributor, who can edit their own draft posts) can call this endpoint with an arbitrary `post_id` and overwrite that post's style meta — combined with Fix 1, this was the mechanism for site-wide stored XSS.

**Fix:**
- Replace the permission callback with a named method that reads `post_id` from the request and checks `current_user_can( 'edit_post', $post_id )`, e.g.:

```php
'permission_callback' => array( $this, 'can_save_style' ),
...
public function can_save_style( $request ) {
    $post_id = (int) $request->get_param( 'post_id' );
    return $post_id && current_user_can( 'edit_post', $post_id );
}
```

- This matches the object-level capability check pattern WP core's own REST controllers use for per-post writes.

## Fix 3 & 4: AJAX pagination handler — template and query injection

**File:** `inc/classes/class-plugin.php`, method `post_crafts_pagination()` (lines 74-104)

**Problem A (Local File Inclusion):** `$_POST['template']` is concatenated directly into a template path passed to `post_crafts_template()`, which does a `file_exists()` check and then `include`s the result. There is no whitelist, so a crafted `template` value containing path traversal can cause inclusion of arbitrary `.php` files elsewhere on the server. The action is registered for `wp_ajax_nopriv_paginate_posts` as well, so this is reachable by unauthenticated visitors (gated only by a generic, non-privileged nonce created for all visitors).

**Problem B (Query injection / data exposure):** `$_POST['query']` is passed directly into `new WP_Query( $_POST['query'] )` with no key restrictions. An anonymous caller can set `post_status` to `private`/`draft`, request `posts_per_page => -1`, or supply arbitrary `meta_query`/`tax_query` values to enumerate unpublished content or trigger expensive queries.

**Fix (allowlist/sanitize in place — chosen over rebuilding the query server-side from stored attributes, to keep the existing request contract and avoid frontend script changes):**

- **Template:** validate `$_POST['template']` against a hardcoded whitelist before use:
  ```php
  $allowed_templates = array( 'pagination', 'loadmore', 'arrow' );
  $template = in_array( $_POST['template'], $allowed_templates, true ) ? $_POST['template'] : 'pagination';
  ```
- **Query:** build a new args array by copying only a fixed set of safe keys from `$_POST['query']`, rather than passing it through wholesale:
  - Allowed keys: `post_type`, `posts_per_page` (cast to int, clamped to a sane max, e.g. 50), `paged`, `orderby`, `order`, `tax_query`, `post__in`, `post__not_in`, `ignore_sticky_posts`.
  - `post_status` is **always** forced to `'publish'` server-side and never taken from client input, regardless of what `$_POST['query']` contains.
- **Input sanitization:** cast `$_POST['postId']` with `absint()` and `$_POST['blockId']` with `sanitize_text_field()` before use in `get_post()` / block-attrs comparison (`post_crafts_get_block_attributes()`), which currently receive raw superglobal values.

No changes to `src/scripts/pagination.js` are required — the request shape (`query`, `template`, `postId`, `blockId`, `paged`) stays the same; only server-side validation is added.

## Fix 5: Block context for current post ID

**Files:** `src/blocks/post-grid/block.json`, `src/blocks/post-list/block.json`, both blocks' `edit.js`, `src/libs/fetchPosts.js`

**Problem:** Neither block declares `usesContext`, so `useFetchPosts` resolves the current post via `select('core/editor').getCurrentPostId()` directly inside the hook (`fetchPosts.js:64`). This only returns a meaningful value on the classic post-edit screen — in Query Loop, Site Editor templates, or reusable blocks used elsewhere, it returns `0`/`undefined`, silently breaking "exclude current post" behavior.

A related, previously-unnoticed bug in the same code path: the `excludeCurrentPost` block attribute is never passed into `useFetchPosts` from either `edit.js` (call sites at `post-grid/edit.js:104-113` and the equivalent in `post-list/edit.js`). The hook unconditionally includes `exclude: [currentPostId]` in its query regardless of the attribute's value, so **editor preview always excludes the current post even when the "exclude current post" toggle is off** — diverging from the front-end, where `post_crafts_query_builder()` (`inc/helpers/custom-functions.php:135-137`) correctly makes exclusion conditional on the attribute.

**Fix:**
1. Add `"usesContext": ["postId", "postType"]` to both `block.json` files. Additive change — no impact on existing saved block markup/attributes.
2. Update both `edit.js` files to accept `context` as an Edit-component prop and resolve the post ID as `context?.postId ?? select('core/editor').getCurrentPostId()` (context takes precedence when supplied; falls back to the existing behavior on the classic editor where no context is provided).
3. Change `useFetchPosts` (`fetchPosts.js`) to accept the resolved post ID and the `excludeCurrentPost` flag as parameters instead of calling the `core/editor` selector internally. Only add the post ID to the query's `exclude` array when `excludeCurrentPost` is `true` — matching server-side logic exactly.

**Explicitly out of scope per decision:** no manual "override post ID" UI control is added for contexts where neither `context.postId` nor the editor selector supplies a value (e.g., a standalone widget area) — exclusion simply becomes a no-op in that case, same as today's effective behavior when `getCurrentPostId()` returns falsy.

## Testing / verification plan

- **Fix 1 (XSS):** Save style content containing `</style><script>alert(1)</script>` via the REST endpoint (as a user who should legitimately be able to), confirm rendered output on the front end has the payload stripped.
- **Fix 2 (IDOR):** As a Contributor-level user, attempt `POST /post-crafts/v1/style` with a `post_id` belonging to another user/post the Contributor cannot edit; confirm `403`. Confirm the legitimate case (editing one's own post, and an Editor/Admin editing any post) still succeeds.
- **Fix 3/4 (AJAX pagination):** Attempt requests with `template=../../../wp-config` and with `query` containing `post_status: ["private"]` / `posts_per_page: -1`; confirm both are neutralized (falls back to default template / forced `publish` status, capped page size). Confirm normal pagination and load-more flows still work end to end in the browser.
- **Fix 5 (block context):** Place a Post Grid/List block inside a Query Loop template in the Site Editor and confirm "exclude current post" now correctly resolves against the looped post rather than being inert. On the classic post-edit screen, confirm existing behavior is unchanged: toggling "exclude current post" on/off correctly changes editor preview, and preview now matches front-end render in both states.

## Out of scope (candidates for a follow-up spec)

- Asset dependency management (`class-assets.php` hardcoded/incomplete script deps instead of the generated `.asset.php` file).
- Accessibility gaps in AJAX-driven pagination (no `aria-live`/focus management on page change).
- `useSelect` selector in `fetchPosts.js` mutating refs as a side effect (anti-pattern, not a correctness bug today).
- Standing up the currently-unused Jest/PHPUnit test scaffolding.
- Minor schema/i18n nits (`excerpt` attribute default is the string `"true"` instead of boolean `true`; missing `translators:` comments; `composer.json` PHP version floor not matching the plugin header).
